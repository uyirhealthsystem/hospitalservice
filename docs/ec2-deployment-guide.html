Getting Hospital Service onto EC2

A one-time setup on the instance, then every push to main tests, builds, and redeploys itself. No Docker, no Kubernetes — a jar, a systemd service, and GitHub Actions doing the SSH work you'd otherwise do by hand.

Words you'll see below

EC2 instance
The single AWS virtual machine the app runs on — no cluster, no autoscaling.
Security group
The instance's firewall. Nothing reaches it unless a rule opens that port.
systemd unit
A small config file that tells Linux how to start, stop, and restart the jar as a background service.
GitHub secret
An encrypted value the workflow can read but no one can view again — how the SSH key gets to Actions safely.
Runner
The disposable GitHub-hosted machine that checks out your code and runs each workflow.
01

Before you start

Check these off first — the pipeline assumes all of them already exist.

  • An EC2 instance is running, and you can already SSH into it with a .pem key.
  • Java is installed on that instance (you've confirmed this already).
  • You have admin access to Paramasivan-BSM/hospitalservice on GitHub, to add repo secrets.
  • The Mongo Atlas password gets rotated before it goes anywhere near this pipeline. The current one has been sitting in application.properties in git history — treat it as burned.
02

Open the doors

In the instance's security group, allow inbound:

TCP 22 — SSH, your IP only TCP 8080 — the app, from wherever needs to call it

Leave everything else closed. The app itself never needs to initiate inbound connections — only outbound, to reach MongoDB Atlas.

03

Prepare the box

SSH in once, by hand, and set up the account and directory the app will live in:

on the EC2 instance 
# a dedicated, unprivileged user — the app never runs as root
sudo useradd -r -d /opt/hospital -s /usr/sbin/nologin hospital
sudo mkdir -p /opt/hospital
sudo chown hospital:hospital /opt/hospital

Then create the environment file the service will read its Mongo connection from — this file never touches git or the pipeline:

/opt/hospital/.env 
SPRING_MONGODB_URI=mongodb+srv://<user>:<rotated-password>@uyirluster.a7yqyi9.mongodb.net/hospital?appName=uyirluster
sudo chown hospital:hospital /opt/hospital/.env
sudo chmod 600 /opt/hospital/.env
!

Keeping the connection string only on the box (not as a GitHub secret) means a compromised workflow run can't exfiltrate it. The pipeline never needs to know it.

04

Install the systemd service

The unit file already lives in the repo at deploy/hospital.service. Copy it onto the box and register it:

deploy/hospital.service 
[Unit]
Description=Uyir Hospital Service
After=network.target

[Service]
User=hospital
WorkingDirectory=/opt/hospital
ExecStart=/usr/bin/java -XX:MaxRAMPercentage=75.0 -jar /opt/hospital/app.jar
EnvironmentFile=/opt/hospital/.env
Restart=on-failure
RestartSec=5
SuccessExitStatus=143

[Install]
WantedBy=multi-user.target
on the EC2 instance 
sudo cp hospital.service /etc/systemd/system/hospital.service
sudo systemctl daemon-reload
sudo systemctl enable hospital
# leave it stopped — there's no app.jar yet until the pipeline delivers one
05

Tell GitHub how to reach it

In the repo: Settings → Secrets and variables → Actions → New repository secret. Add exactly three:

SecretValue
EC2_HOSTThe instance's public IP or DNS name
EC2_USERThe SSH login user — ec2-user or ubuntu, depending on the AMI
EC2_SSH_KEYThe full private key contents (the .pem file), not the public key
06

How the pipeline actually runs

Every push or PR to main runs test. Only a push that lands on main — after tests pass — runs deploy:

.github/workflows/deploy.yml 
# test job
./mvnw -B test

# deploy job (needs: test)
./mvnw -B -DskipTests package
mv target/*.jar target/app.jar
scp target/app.jar  →  EC2_HOST:/opt/hospital/
ssh EC2_HOST  "sudo systemctl restart hospital"

The runner builds the jar itself each time — it never trusts an artifact from a previous run. The instance only ever receives a finished jar and one restart command.

07

Trigger the first deploy

  1. Commit and push to main (or merge a PR into it).
  2. Open the Actions tab on GitHub — you'll see test start immediately.
  3. Once it's green, deploy starts: build, then the two accent steps from the diagram above — scp, then ssh.
  4. A finished run means systemctl is-active hospital printed active on the box.
08

Prove it's alive

from your machine 
curl http://<EC2_HOST>:8080/actuator/health
→ {"status":"UP"}

curl -X POST http://<EC2_HOST>:8080/api/hospital/doctors/search \
     -H "Content-Type: application/json" -d "{}"
→ paginated list of doctors
on the EC2 instance, if you want the detail 
systemctl status hospital
journalctl -u hospital -f   # tail live logs
09

When it breaks

SymptomLikely cause & fix
Actions: Permission denied (publickey)The EC2_SSH_KEY secret has the wrong key, is missing its BEGIN/END lines, or EC2_USER doesn't match the AMI's default login.
Actions: scp step times outSecurity group isn't allowing port 22 from GitHub's runner IPs, or the instance is stopped.
systemctl status hospital shows failedCheck journalctl -u hospital -e. Usually a missing/misnamed .env, or the Mongo URI is unreachable (password not rotated everywhere, or Atlas network access list blocks the EC2 IP).
curl from your machine hangs or refusesPort 8080 isn't open inbound in the security group, or the service isn't actually running yet — check systemctl status first.
Deploy job succeeds but old behavior is still livesystemctl restart ran before the new jar finished copying. Re-run the workflow; the scp step must complete before ssh starts.
10

What's next

This gets you a working, auto-deploying single box. Once that's stable, worth revisiting:

  • Auth. SecurityConfig currently permits every request unauthenticated — fine for this stage, not once real patient data is behind it.
  • HTTPS. Put nginx or an AWS ALB in front of port 8080 once this is reachable outside your own testing.
  • Rollback. Right now a bad deploy means fixing forward. Keeping the previous app.jar as app.jar.bak before overwriting it is a cheap first step.
