The big picture

Before any commands: here's what you're actually building. Two things happen — shipping your code (top row) and running it (bottom row). Your database stays outside the cluster entirely, in MongoDB Atlas.

Words you'll see below

Image
Your app + everything it needs to run, packaged once by Docker.
Container
An image, actually running.
Pod
One running copy of your container, managed by Kubernetes.
Node
A real server (EC2 instance) that runs your pods.
Deployment
The rule "keep N copies of this pod running, always."
Service
A stable internal address for your pods, even as individual pods come and go.
Ingress / ALB
The door from the public internet into your cluster.
Namespace
A folder-like grouping so multiple microservices share a cluster without colliding.
HPA
Horizontal Pod Autoscaler — adds/removes pod copies automatically based on load.
PDB
Pod Disruption Budget — stops K8s taking down too many pods at once during maintenance.
EKS
AWS's managed Kubernetes — AWS runs the hard control-plane parts for you.
ECR
AWS's private storage for container images — like a private Docker Hub.
kubectl
The command-line tool you use to talk to a Kubernetes cluster.
eksctl
A CLI that turns "create an EKS cluster" into one command instead of dozens of manual steps.
01

Before you start

Tools to install, and one thing to know before you swipe your card.

This costs real money

Nothing in this guide is free. An EKS cluster left running racks up charges by the hour whether or not you're using it — control plane, EC2 nodes, a NAT gateway, a load balancer. Ballpark it at roughly $7–9 a day if you leave everything on. That's not a reason to skip this — it's why step 11, shutting it down, is not optional homework. Bookmark it now.

Install these, then verify each one actually responds:

terminal — verify tooling
# AWS CLI v2
aws --version
# kubectl - talks to any Kubernetes cluster
kubectl version --client
# eksctl - creates/manages EKS clusters
eksctl version
# helm - installs packaged Kubernetes apps (you'll need it for step 07)
helm version
# Docker - builds and runs the image
docker --version

You'll also need an AWS account with billing enabled, and IAM credentials (access key + secret) for a user with enough permissions to create clusters, IAM roles, and load balancers. Using an admin-level user for this first run is fine — just don't leave it that way once this becomes routine.

02

Connect to AWS

Tell the CLI who you are.

terminal
aws configure
# it will prompt for:
#   AWS Access Key ID
#   AWS Secret Access Key
#   Default region name      -> ap-south-1
#   Default output format    -> json

ap-south-1 (Mumbai) is a good default here specifically because your MongoDB Atlas cluster already lives there — keeping the app and the database in the same region cuts network latency and avoids cross-region data transfer charges. Use a different region if you have a reason to.

terminal — checkpoint
aws sts get-caller-identity
You'll know it worked when

You see your Account ID and an ARN back, not an error.

03

Create the cluster

This is the slow one — go make tea.

terminal — takes 15–20 minutes
eksctl create cluster --name uyir-cluster --region ap-south-1 --version 1.30 --with-oidc --nodegroup-name standard-workers --node-type t3.medium --nodes 3 --nodes-min 3 --nodes-max 6 --managed

eksctl is doing a lot here quietly: a VPC spread across three availability zones, the EKS control plane, and a managed group of three worker nodes — one of the things that makes this setup resilient to an entire AWS zone having a bad day. --with-oidc sets up something step 07 needs later, so it's worth including now rather than retrofitting it.

Note

--nodes-min/--nodes-max only set the boundaries an autoscaler is allowed to work within — they don't make scaling happen by themselves. Nothing will actually add nodes automatically yet; that needs Cluster Autoscaler or Karpenter, which this guide doesn't set up (see what's next). Pod-level autoscaling in step 09 works without it.

Point kubectl at it

eksctl does this automatically, but confirm it:

terminal — checkpoint
kubectl get nodes
You'll know it worked when

Three node names show up, all with status Ready.

One more piece: metrics-server

EKS doesn't ship this by default, but the autoscaler in step 09 needs it to know how busy your pods actually are:

terminal
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
The gotcha nobody warns you about

Your MongoDB Atlas cluster only accepts connections from IP addresses you've explicitly allowed. Right now that's probably just your laptop. Once your pods start connecting, they'll come from your VPC's NAT Gateway IP, not your laptop's. Find it and allow it in Atlas before step 06, or your pods will pass every check except actually reaching the database — and readiness will fail forever with no obvious clue why.

terminal — find the IP to allowlist
aws ec2 describe-nat-gateways --region ap-south-1 --query "NatGateways[].NatGatewayAddresses[].PublicIp" --output text

Add whatever IP(s) that prints to Atlas → Network Access → Add IP Address.

04

Build & push the image

Give Kubernetes something to run.

Create somewhere for the image to live:

terminal
aws ecr create-repository --repository-name hospital-service --region ap-south-1

The output includes a repositoryUri — something like 123456789012.dkr.ecr.ap-south-1.amazonaws.com/hospital-service. Copy it; you'll use it in every command below and again in step 06.

terminal — log in, build, tag, push
# authenticate Docker against your ECR registry
aws ecr get-login-password --region ap-south-1 | docker login --username AWS --password-stdin <ECR_REPO_URI>

# build, from the repo root where the Dockerfile lives
docker build -t hospital-service:v1 .

# tag it for ECR
docker tag hospital-service:v1 <ECR_REPO_URI>:v1

# push
docker push <ECR_REPO_URI>:v1
Tip

Use a real tag like v1 or a git commit SHA, never latest. With latest, two different deploys can point at the exact same tag while pointing at completely different code — there's no way to tell what's actually running, and no way to roll back to a specific version.

05

Configure the secret

Give the app its database credentials, without putting them in git.

First, create the namespace everything else in this guide lives in:

terminal
kubectl apply -f k8s/00-namespace.yaml
Don't

k8s/01-secret.example.yaml in the repo is a template with placeholder values — it is not meant to be applied as-is, and a real one should never be committed to git. Create the real secret directly from the command line instead:

terminal
kubectl create secret generic hospital-service-secrets --namespace uyir --from-literal=SPRING_MONGODB_URI="mongodb+srv://<user>:<password>@uyirluster.a7yqyi9.mongodb.net/hospital?appName=uyirluster"
terminal — checkpoint
kubectl get secret hospital-service-secrets -n uyir

Longer term, look at the External Secrets Operator pulling from AWS Secrets Manager instead of hand-typing this — it means the credential lives in exactly one place instead of scattered across terminal history.

06

Deploy the app

Actually run it.

Open k8s/02-deployment.yaml and replace the placeholder image with the real one you pushed in step 04:

k8s/02-deployment.yaml
# before
image: <ECR_REPO_URI>/hospital-service:<TAG>

# after, e.g.
image: 123456789012.dkr.ecr.ap-south-1.amazonaws.com/hospital-service:v1

Then apply the core resources — everything except the Ingress, which needs step 07 first:

terminal
kubectl apply -f k8s/02-deployment.yaml -f k8s/03-service.yaml -f k8s/04-hpa.yaml -f k8s/05-pdb.yaml
terminal — watch it start (Ctrl+C once all three are Running)
kubectl get pods -n uyir -w
You'll know it worked when

Three pods show 1/1 Running. If a pod is stuck otherwise, jump to when it breaks.

07

Expose it to the internet

This is the fiddliest step. Take it slowly.

Your Service is reachable inside the cluster, but nothing outside it yet. That needs the AWS Load Balancer Controller — a piece of software that watches for Ingress resources and provisions a real Application Load Balancer for each one. It isn't built into EKS; you install it once per cluster.

7a. Give it permission to create AWS resources

terminal
curl -o iam-policy.json https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/main/docs/install/iam_policy.json

aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy --policy-document file://iam-policy.json

Copy the policy ARN from the output, then attach it to a dedicated service account:

terminal — replace <AWS_ACCOUNT_ID>
eksctl create iamserviceaccount --cluster=uyir-cluster --region=ap-south-1 --namespace=kube-system --name=aws-load-balancer-controller --attach-policy-arn=arn:aws:iam::<AWS_ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy --approve

7b. Install the controller with Helm

terminal
helm repo add eks https://aws.github.io/eks-charts
helm repo update

helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system --set clusterName=uyir-cluster --set serviceAccount.create=false --set serviceAccount.name=aws-load-balancer-controller
terminal — checkpoint
kubectl get deployment aws-load-balancer-controller -n kube-system
You'll know it worked when

The READY column shows 2/2.

7c. Now open the door

terminal
kubectl apply -f k8s/06-ingress.yaml

# wait a minute or two, then:
kubectl get ingress hospital-service -n uyir

The ADDRESS column fills in with your ALB's public DNS name once it's provisioned — that's your public URL.

Before you point real traffic at this

The manifest itself carries this warning, worth repeating here: this app's SecurityConfig currently permits every request, unauthenticated. That's fine for the verification in the next step — it is not fine for anything beyond it. Put real auth in front of this before it sees traffic that matters.

08

Prove it works

From outside the cluster, over the real internet.

terminal — replace <ALB_DNS_NAME>
curl "http://<ALB_DNS_NAME>/api/hospitals"

Swagger UI is live too, at http://<ALB_DNS_NAME>/swagger-ui.html — useful for poking at every endpoint by hand without writing curl commands. If you use the Postman collection from earlier, update its baseUrl variable to this same ALB DNS name.

09

Confirm it's actually HA

Don't just take the manifest's word for it.

terminal
kubectl get hpa -n uyir
kubectl get pdb -n uyir
kubectl get pods -n uyir -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName
kubectl get nodes -L topology.kubernetes.io/zone

Cross-reference the last two outputs: your three pods should be landing on nodes in three different zones, not all piled onto one. That's what topologySpreadConstraints in the Deployment is doing — if one AWS availability zone has an outage, the other two pods keep serving traffic.

The HPA will scale pod count up under load (3 → 10, per k8s/04-hpa.yaml) — but remember from step 03, nothing will add more nodes to make room for them yet without Cluster Autoscaler or Karpenter. For now, keep an eye on kubectl get nodes capacity if you're deliberately load-testing.

10

When it breaks

It will. Here's where to look first.

Pod stuck Pending
Usually not enough node capacity to schedule it.
kubectl describe pod <name> -n uyir — check the Events at the bottom.
ImagePullBackOff
Wrong image URI/tag in the Deployment, or the ECR login expired.
kubectl describe pod <name> -n uyir — re-check the image string against what step 04 actually pushed.
CrashLoopBackOff
The app is starting, then dying — almost always a bad or missing secret.
kubectl logs <name> -n uyir --previous
Pod runs, but readiness never turns green
The app is up but can't reach MongoDB — nine times out of ten, this is the Atlas IP allowlist from step 03.
kubectl logs <name> -n uyir — look for a Mongo connection timeout.
Ingress ADDRESS never fills in
The Load Balancer Controller isn't running, or its IAM permissions are wrong.
kubectl get pods -n kube-system and kubectl logs deployment/aws-load-balancer-controller -n kube-system
ALB responds, but with 502/503
Pods aren't passing their health check yet, or the health-check path is wrong.
Confirm alb.ingress.kubernetes.io/healthcheck-path in k8s/06-ingress.yaml matches /actuator/health.
11

Shut it down

The step people skip, and then get a surprise bill.

Rough illustrative costs if all of this is left running — check current AWS pricing for exact numbers:

ResourceApprox. cost
EKS control plane~$0.10 / hr
3× t3.medium nodes~$0.12 / hr
NAT Gateway~$0.045 / hr + data
Application Load Balancer~$0.025 / hr + data
Roughly, per day$7–9 / day

Tear down in this order — the Ingress first, so the ALB is deprovisioned cleanly before the cluster disappears under it:

terminal
kubectl delete -f k8s/06-ingress.yaml

# wait a minute, then confirm the ALB is gone
aws elbv2 describe-load-balancers --region ap-south-1

kubectl delete -f k8s/02-deployment.yaml -f k8s/03-service.yaml -f k8s/04-hpa.yaml -f k8s/05-pdb.yaml

helm uninstall aws-load-balancer-controller -n kube-system

# tears down nodes, VPC, everything eksctl created - takes ~10 minutes
eksctl delete cluster --name uyir-cluster --region ap-south-1

aws ecr delete-repository --repository-name hospital-service --region ap-south-1 --force
Double-check

Peek at the AWS Console once afterward: EC2 → Instances (should be empty), VPC → NAT Gateways (occasionally one survives a botched teardown and keeps billing quietly).

12

What's next

This guide covers one service. You said there are more.

  • Repeat steps 04–07 for each additional microservice — they can all share this same cluster and the uyir namespace.
  • Once there are several of them talking to each other, revisit a service mesh (Istio, Linkerd, App Mesh) for automatic retries, mTLS, and cross-service observability — deliberately skipped here in favor of plain Kubernetes DNS.
  • Replace the by-hand build/push/apply cycle with CI/CD, so a merge deploys itself.
  • Add Cluster Autoscaler or Karpenter for real node-level autoscaling under sustained load.
  • Put real authentication in front of the API before it carries traffic that matters.
Files referenced throughout: Dockerfile, .dockerignore, and k8s/00–06 in the repo.
